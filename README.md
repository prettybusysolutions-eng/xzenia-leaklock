# LeakLock

LeakLock analyzes structured billing exports for patterns that may indicate
missed or eroding revenue. It produces an evidence-oriented review queue; it
does not guarantee that an estimate is collectible or recovered.

The current implementation is a Flask and PostgreSQL application with a
deterministic CSV/XLSX scanner, signed scan-result links, optional accounting
connectors, Stripe checkout plumbing, and governed action tracking.

## What It Detects

The scanner looks for supported patterns such as:

- failed payments that appear unrecovered;
- inconsistent pricing for comparable services;
- discount drift;
- possible duplicate billing;
- credits, refunds, or usage records that need review.

Detection depends on the columns and evidence present in the supplied export.
Every finding should be reviewed against the source billing system before
someone changes an invoice, contacts a customer, or claims recovered revenue.

## Truth Boundaries

- Findings are estimates and review prompts, not accounting conclusions.
- A detected amount is not proof that the amount is legally owed or
  collectible.
- The bundled sample is synthetic and proves software behavior only.
- LeakLock is not currently represented as HIPAA compliant. Do not upload PHI
  or other regulated data without an appropriate security review, deployment,
  and contractual controls.
- Commercial pricing is being reconciled. Repository examples are not a
  binding offer.

## Quick Verification

Prerequisites:

- Python 3.11 or newer
- `libmagic`
- PostgreSQL for the web application

Run the scanner against synthetic data without configuring a database:

```bash
git clone https://github.com/prettybusysolutions-eng/xzenia-leaklock.git
cd xzenia-leaklock

python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements-lock.txt

python scripts/scan_sample.py
python -m pytest -q
```

The sample command reports only synthetic values from
`static/sample_data.csv`.

For a one-command isolated verification from a fresh clone:

```bash
./scripts/verify_fresh_clone.sh
```

## Local Web Application

Create a PostgreSQL database, then configure the environment:

```bash
cp .env.example .env

export DATABASE_URL=postgresql://postgres:password@localhost:5432/leaklock
export FLASK_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')"
export LEAKLOCK_ADMIN_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"

gunicorn "app:create_app()" --bind 127.0.0.1:5050
```

Useful local endpoints:

- `GET /live`: process liveness
- `GET /health`: database-aware readiness
- `GET /upload`: file upload workflow
- `GET /demo`: synthetic demonstration

Scan results and reports require a signed, expiring access token generated by
the server. System 6 operations require an API key.

## Architecture

```text
CSV/XLSX upload or connector
            |
            v
  deterministic scanner
            |
            v
 estimated findings + evidence
            |
      +-----+------+
      |            |
 signed report   governed action lifecycle
 access          approval -> execution -> evidence
      |            |
      +-----+------+
            |
        PostgreSQL
```

Important modules:

- `csv_scanner.py`: structured-file parsing and leak-pattern analysis
- `routes/`: Flask upload, report, checkout, webhook, and operations routes
- `scan_access.py`: signed, expiring scan authorization
- `services/consequence.py`: evidence-bound recommendation intake
- `models/db.py`: PostgreSQL persistence and governed action lifecycle
- `tests/`: scanner, security, offer-boundary, and lifecycle tests

## Configuration

| Variable | Purpose |
| --- | --- |
| `DATABASE_URL` | PostgreSQL connection URL |
| `FLASK_SECRET_KEY` | Flask sessions and signed scan access |
| `LEAKLOCK_ENV` | Set to `production` in production |
| `SCAN_ACCESS_MAX_AGE` | Signed scan-link lifetime in seconds |
| `LEAKLOCK_ADMIN_KEY` | API-key administration |
| `STRIPE_SECRET_KEY` | Optional Stripe checkout and direct scan |
| `STRIPE_WEBHOOK_SECRET` | Required for Stripe webhook verification |
| `LEAKLOCK_DOMAIN` | Public application origin |
| `TOKEN_ENCRYPTION_KEY` | Connector-token encryption |
| `SMTP_*` | Optional payment email delivery |

Production startup rejects the known development Flask secret. Readiness
returns HTTP 503 when PostgreSQL is unavailable.

## Security Model

- Uploaded file names, extensions, size, and MIME type are validated.
- Raw upload bytes are processed in memory. Derived scan findings may be
  persisted in PostgreSQL.
- Result and report routes require a signed token bound to the scan ID.
- Operational action routes require `X-API-Key`.
- Stripe webhooks require signature verification and use idempotent payment
  records.
- Demo and sample evidence is marked synthetic and excluded from real-outcome
  proof metrics.

See [BUYER-READINESS-AUDIT.md](BUYER-READINESS-AUDIT.md) for the current audit,
remaining release blockers, and buyer-ready exit criteria.

## Status

LeakLock is a working prototype under active hardening. Before handling
customer billing exports, it still needs a controlled security review, a
canonical commercial contract, retention/deletion operations, and a measured
pilot that distinguishes estimated leakage from verified recovery.
